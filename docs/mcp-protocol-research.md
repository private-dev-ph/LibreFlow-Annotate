# MCP protocol and security research

Checked **2026-11-14** against official specifications, SDK documentation, and GitHub releases. Research only; no application changes. Uppercase **MUST/SHOULD/MAY** below preserve normative requirements; **Planning recommendation** identifies local judgment. The current [latest specification](https://modelcontextprotocol.io/specification/latest) resolves to **2026-07-28**. Do not implement a 2025 lifecycle while claiming only this revision.

## Protocol compatibility

| Concern | Modern: 2026-07-28 | Legacy: 2025-11-25 and earlier |
| --- | --- | --- |
| Startup | No initialization handshake; every request is independently understood. Servers MUST implement `server/discover`; clients MAY call it first. | `initialize` MUST be the first interaction; version/capabilities are negotiated before normal operation. |
| Versions | Unsupported revisions MUST return `-32022` with supported versions; clients SHOULD retry a mutual version. | Version agreed during initialization. |
| Supporting both | A server MAY implement both eras. Transport-specific detection distinguishes a recognized modern error from a legacy fallback. | Support is an explicit compatibility commitment. |

Sources: [modern versioning](https://modelcontextprotocol.io/specification/2026-07-28/basic/versioning.md), [legacy lifecycle](https://modelcontextprotocol.io/specification/2025-11-25/basic/lifecycle).

Modern requests MUST carry `io.modelcontextprotocol/protocolVersion` and `io.modelcontextprotocol/clientCapabilities` in `params._meta`. `clientInfo` is optional, but clients SHOULD include it. Missing required fields produce `-32602` and HTTP 400. Servers MUST NOT infer capabilities, identity, or conversation state from prior requests or a reused process. Cross-request application state MUST use explicit identifiers. Modern results MUST include `resultType`; clients MUST interpret its absence from older servers as `complete`. JSON Schema 2020-12 support is required; remote `$ref` fetching MUST NOT happen automatically. [Base protocol](https://modelcontextprotocol.io/specification/2026-07-28/basic)

**Modern HTTP:** One endpoint MUST support POST; each request is its own POST. Clients MUST accept both JSON and request-scoped SSE responses. There is no protocol session, standalone GET stream, or resumable `Last-Event-ID`. Notifications use `subscriptions/listen`. Required headers include `MCP-Protocol-Version`, `Mcp-Method`, and `Mcp-Name` for tool calls/resource reads/prompt retrieval; mirrored values must match the body. Servers MUST validate Origin and reject invalid present origins with 403; local servers SHOULD bind loopback. [Modern Streamable HTTP](https://modelcontextprotocol.io/specification/2026-07-28/basic/transports/streamable-http)

**Legacy only:** Streamable HTTP replaced 2024-11-05 HTTP+SSE in 2025-03-26. A 2025 server MAY create `MCP-Session-Id`; once issued, clients MUST send it subsequently. Legacy deployments may have GET streams, replay, and session termination. These are not modern requirements. [Legacy transports](https://modelcontextprotocol.io/specification/2025-11-25/basic/transports)

**stdio:** Host launches a subprocess; newline-delimited JSON-RPC uses stdin/stdout. stdout MUST contain only MCP messages; logging belongs on stderr. Modern stdio still carries per-request metadata. [stdio binding](https://modelcontextprotocol.io/specification/2026-07-28/basic/transports/stdio)

## Remote authorization requirements

The protocol makes authorization optional in general; HTTP implementations supporting it SHOULD follow the MCP authorization specification. An authorization server MUST implement OAuth 2.1. stdio SHOULD instead obtain credentials from the environment. Bearer authorization MUST accompany every protected HTTP request and MUST NOT be in query strings. Invalid/expired tokens require 401; insufficient permissions require 403. Clients MUST send the canonical MCP resource URI in both authorization and token requests. Before redirecting, clients MUST record the validated issuer; returned `iss` must match exactly when present, and must be present if support was advertised. Authorization servers SHOULD emit `iss` and MUST advertise doing so. Scope challenges are authoritative for the current operation; servers SHOULD supply required scopes. [Authorization](https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization)

**Discovery:** MCP servers MUST publish RFC 9728 Protected Resource Metadata containing at least one `authorization_servers` entry and MUST offer discovery through a 401 `resource_metadata` challenge or well-known URI. Clients MUST support both, prefer the challenge, and support OAuth metadata and OIDC discovery. For issuers with paths, follow the documented endpoint ordering. Returned issuer MUST exactly equal the discovery issuer; mismatches MUST be rejected. Registration credentials/tokens MUST be separate per authorization server. [Discovery requirements](https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization/authorization-server-discovery)

**Registration:** Clients and authorization servers SHOULD support Client ID Metadata Documents (CIMD). Clients supporting all choices SHOULD prefer existing pre-registration, then CIMD, then Dynamic Client Registration (DCR), then manual client information. DCR is deprecated compatibility functionality, not a mandatory new-server endpoint. CIMD client IDs MUST be HTTPS URLs with paths; document `client_id` MUST exactly match its URL, and required metadata/redirect URIs MUST be validated. [Client registration](https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization/client-registration.md)

**Token and authorization security:** Servers MUST validate tokens for their intended MCP audience before processing; an upstream API token is separate, and inbound token passthrough MUST NOT occur. Clients MUST use PKCE, verify metadata advertises support, and use S256 when technically capable; absent `code_challenge_methods_supported` means refuse authorization. Authorization endpoints MUST use HTTPS; redirect URIs MUST be localhost or HTTPS and exactly validated. Clients SHOULD verify OAuth state. Tokens MUST be securely stored; authorization servers SHOULD issue short-lived access tokens and MUST rotate refresh tokens for public clients. A proxy using a static upstream client ID MUST obtain consent for each dynamically registered client. [Authorization security](https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization/security-considerations)

OAuth discovery and CIMD fetches create SSRF exposure. Official security guidance requires server-hosted clients to implement appropriate mitigations and recommends HTTPS, private/reserved address restrictions, redirect revalidation, and DNS-rebinding defenses. Authorization URLs MUST be validated and MUST NOT be opened through a shell. [Security best practices](https://modelcontextprotocol.io/docs/2026-07-28/tutorials/security/security_best_practices)

## Tool contracts

Servers supporting tools MUST declare the capability and answer `tools/list` for the current authorization. Tool availability MAY vary by per-request authorization but MUST NOT vary because of connection state; stable ordering is a SHOULD. Servers MUST validate inputs, enforce access control, rate limit, and sanitize outputs. Tool definitions carry input schemas; supplied output schemas require conforming structured results, which clients SHOULD validate. Returning serialized JSON in a text block alongside structured results is a SHOULD for backwards compatibility. Use JSON-RPC errors for malformed requests/unknown tools; actionable execution, argument-validation, and business failures use `isError: true`. [Tools](https://modelcontextprotocol.io/specification/2026-07-28/server/tools)

`readOnlyHint`, `destructiveHint`, `idempotentHint`, and `openWorldHint` are descriptive hints, not security boundaries. Their defaults are respectively false, true, false, true. [Tool annotations schema](https://modelcontextprotocol.io/specification/2026-07-28/schema#toolannotations)

Protocol list pagination uses opaque `cursor`/`nextCursor`, with server-controlled page sizes. Clients MUST NOT parse cursors or assume a fixed page size; servers SHOULD provide stable cursors and handle invalid ones. This covers tools/resources/prompts catalog listings; pagination inside a domain tool result needs its own explicit schema. [Pagination](https://modelcontextprotocol.io/specification/2026-07-28/server/utilities/pagination)

## Planning recommendations and unresolved gates

- For the selected-project, read-only MVP, keep project authorization in shared application services; validate a requested project against the authenticated principal and grant on every request. Transport session IDs, client metadata, tool annotations, filesystem roots, and a model-supplied project ID cannot substitute for authorization.
- A local stdio bridge should call authenticated application services rather than write project JSON directly. Supply only scoped credentials in its environment and keep stdout clean. Local stdio is an ordinary OS process, not a protocol sandbox; minimal environment/OS access and reviewed pinned binaries are prudent. [Official local-server guidance](https://modelcontextprotocol.io/docs/2026-07-28/tutorials/security/local-server-security.md)
- Keep local bridge credentials distinct from remote OAuth access tokens. Decide canonical resource URI, issuer, exact redirect registration, project grant storage/revocation, and least-privilege scopes before implementation.
- Choose and pin a released SDK after checking the application's Python/Node baseline. Exercise 2026-07-28 and the specific older revision(s) promised to users over both selected transports, including bad/missing metadata, Origin, token audience/expiry, and cross-project denial.
- Validate the actual desired host clients and identity provider. SDK and Inspector compatibility are documented; no target host, provider, or deployed gateway has been exercised by this research.
